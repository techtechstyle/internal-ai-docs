# セキュリティルールと権限ベースライン

`🟢 全員`

本書は、当チームが定める禁止事項と、権限設定の標準ベースラインを記載します。違反はインシデント報告の対象です。

リポジトリ内のコードを AI に読ませること自体は、会社が契約する有料プランの利用規約の範囲内で、業務利用として認められています。一方で、`.env` などのシークレットや顧客の個人データは、次の禁止事項のとおり権限設定で機械的にブロックします。契約プランのデータ取り扱い条件の詳細は、AI 推進チームが管理します。

## 全員が守る禁止事項

- 機密ファイル(`.env`、鍵ファイル、顧客データ)を AI に読ませません(権限設定でもブロックしていますが、意図的な回避も禁止です)
- `bypassPermissions`(いわゆる YOLO モード)を通常業務で使いません
- 「絶対禁止」の統制を CLAUDE.md の記述だけに頼りません([解説: Claude Code とは](../explanation/what-is-claude-code.md)の「お願いと強制の違い」を参照)
- 出所不明のプラグイン・MCP サーバーをインストールしません(プラグインはユーザー権限で任意コードを実行できる、高度に信頼されたコンポーネントです)。使いたいものがあれば AI 推進チームに申請し、承認後に `.mcp.json` やチームマーケットプレイスへの追加 PR として反映します

## ヘッドレスモード・CI での自動実行

現在の標準は、読み取り専用の PR 自動レビュー(`max_turns` 上限つき、Write 権限なし)のみです。書き込みを伴う自動化は、AI 推進チームの設計レビューを経て、ワークフロー単位で許可します。段階的な許可範囲の拡大は、[導入ロードマップ](../../ROADMAP.md)のステージ2〜3に記載しています。

## チーム標準の権限ベースライン

以下は、リポジトリにコミット済みの標準設定です。内容を変更する場合は、必ずプルリクエスト(PR)レビューを通します。個人運用の間はセルフチェックで構いませんが、deny ベースラインは同じ内容を、必ず自分の `settings.json` にも設定します。

`.claude/settings.json`(チーム標準・抜粋)

```json
{
  "permissions": {
    "deny": [
      "Read(**/.env)",
      "Bash(sudo:*)",
      "Bash(curl:*)",
      "Bash(wget:*)",
      "Bash(rm -rf:*)"
    ],
    "allow": [
      "Bash(npm run lint)",
      "Bash(npm test)",
      "Bash(git status)"
    ]
  }
}
```

deny は、シークレットの読み取り・管理者権限の実行・外部への無断送信・破壊的削除を防ぎます。allow は、既知の安全なコマンドを確認なしで許可します。

自分の環境で deny が効いているかを確かめるには、Claude に「.env の中身を見せて」と依頼します。ブロックされれば正常です。ブロックされない場合は設定が読み込まれていません。リポジトリ直下で起動しているかを確認します。

### deny ルールの書き方: Good パターンとアンチパターン

deny は allow で例外を作れません。広すぎる deny は、チーム全員の作業を止めます。

#### ✅ Good パターン: 危険な操作だけを狙い撃つ

```json
"deny": [
  "Bash(aws s3 rm:*)",
  "Bash(aws ec2 terminate-instances:*)",
  "Bash(aws iam:*)"
]
```

削除・インスタンス停止・権限操作という、取り返しのつかない操作だけをブロックします。`aws s3 ls` のような参照系の日常作業は通ります。

#### ❌ アンチパターン: ワイルドカードで全部止める

```json
"deny": [
  "Bash(aws *)"
]
```

安全な参照コマンドまで全滅し、メンバーは毎回手動で AWS CLI を実行することになります。不便さから、deny 回避や YOLO モードの誘惑も生まれます。厳しすぎるルールは、緩いルールより危険な運用を招きます。
