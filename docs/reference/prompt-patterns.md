# 指示文の Good パターンとアンチパターン

`🔵 SE`

本書は、Claude Code への指示文(プロンプト)を書くときの Good パターンとアンチパターンを記載します。ワークフローの各ステップの質は、最初の指示文でほぼ決まります。

## 良い指示文の3点セット

良い指示文は、次の3点をそろえます。

| 要素 | 内容 |
| --- | --- |
| 対象 | 何を対象にするかを具体的に特定する |
| 完了条件 | 機械的に判定できる基準(テストが通る等) |
| 変更しない範囲 | 触ってはいけないファイル・仕様を明示する |

## Good パターン

```text
POST /login が 500 を返すバグを修正して。
進め方:
1. まず原因を調査して報告(planモード)
2. 実装計画を出して承認を待つ
3. 承認後に実装
完了条件:
- npm test auth が全件パスすること
制約:
- src/legacy/ 配下は変更しない
- DB スキーマは変えない
```

対象が特定され、機械的に判定できる完了条件があり、触ってはいけない範囲も明示されています。テストが通るまで自走でき、勝手な範囲拡大も防げます。

## アンチパターン

```text
ログイン周りのバグ、直しておいて。
ついでに気になるところがあったら
きれいにしておいて。
```

3つの問題があります。

- どのバグかを特定できず、探索が発散する
- 完了条件がないため、実際は未解決でも「完了した」ように見える状態で止まる
- 「ついでにきれいに」が際限のない範囲拡大を招き、レビューできない巨大な差分を生む
