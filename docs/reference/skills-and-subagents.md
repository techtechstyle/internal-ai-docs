# スキル・サブエージェントの使い分けと書式

`🔵 SE`

本書は、CLAUDE.md・フック・スキル・サブエージェントなど拡張機構の使い分け判断基準と、SKILL.md・サブエージェント定義ファイルの書式を記載します。対象バージョン: v1.6由来。

## 拡張機構の使い分け判断表

書きたい内容から、正しい置き場所を判定する表です。

| 書きたい内容 | 正解の置き場所 | 理由 |
| --- | --- | --- |
| ビルドコマンド、規約などの事実 | `CLAUDE.md`(ルート) | 毎セッション必要な基礎知識 |
| 「Xのたびに必ずYする」 | フック | お願いでなく強制すべき自動処理 |
| 「これは決してするな」 | PreToolUse フックまたは権限 deny | 破られてはいけない禁止事項 |
| 30行くらいある手順書 | スキル | 必要なときだけ読み込まれ、机を汚さない |
| 特定API・ディレクトリ限定のルール | `.claude/rules/` + `paths:` | 関係ないセッションに影響しない |
| 個人の好み(口調、エディタ等) | ユーザーレベルのファイル | チームに押し付けない |
| 調査・ログ分析など使い捨ての大仕事 | サブエージェント | 別の机で作業し、要約だけ持ち帰る |

## SKILL.md の description:Good パターンとアンチパターン

スキルは、名前と description だけが常時読み込まれ、本文はタスクが合致したときだけ読み込まれる段階的開示のしくみです。必要なときだけ読み込まれるため、手順書をスキル化しても CLAUDE.md を肥大化させません。Claude は description だけを頼りに多数のスキルから選ぶため、次の点が発動精度を左右します。

### Good パターン

```yaml
description: 本番デプロイ前の確認手順。
  デプロイ、リリース、本番反映の作業や
  その準備を行うときに必ず使用する。
```

「何をするか(確認手順)」と「いつ使うか(デプロイ・リリース・本番反映)」の両方が含まれ、関連する言い回しも列挙されています。

### アンチパターン

```yaml
description: デプロイ用
```

「何をするか」と「いつ使うか」のどちらも具体性を欠くため、「リリース作業して」のような依頼と照合できません。作成しても使われないスキルの大半は、description の情報不足が原因です。

> **NOTE:** フロントマターに `disable-model-invocation: true` を付けると、AI が自動で発動せず、`/スキル名` で人間が明示的に呼び出す専用のスキルになります。旧来のカスタムスラッシュコマンドは、この形式に統合されました。

## サブエージェント定義ファイルの書式

サブエージェントは `.claude/agents/` に置く定義ファイルです。独自のコンテキストウィンドウで作業し、最終的な要約だけをメインセッションへ返します。深い調査・ログ分析・依存関係の監査など、後で参照しない中間結果で机を散らかす作業に向きます。

### 記載例:`.claude/agents/security-reviewer.md`

```yaml
---
name: security-reviewer
description: 差分のセキュリティ観点レビュー。PR前に使用。
tools: Read, Grep, Glob, Bash
model: opus
---
あなたはセキュリティレビュアーです。与えられた差分について、
正しさと明示された要件に影響する問題だけを指摘してください。
```

| フィールド | 内容 |
| --- | --- |
| `name` | サブエージェントの識別名 |
| `description` | 用途と使用タイミング(SKILL.md と同様、具体性が発動精度を左右する) |
| `tools` | 使用を許可するツールの一覧 |
| `model` | 使用するモデル。サブエージェントごとに指定できる |

> **NOTE:** サブエージェントごとにモデルを指定できます。調査系は軽量なモデル、レビューは中位以上のモデルといった振り分けが公式に推奨されています。
