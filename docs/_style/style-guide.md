## 1. 設計原則 — 3軸から実装への写像

すべての規則は、次の3軸のいずれかに根拠を持たなければならない。根拠のない規則は追加しない(規則自体が認知的負荷であるため)。

| 設計軸 | 根拠理論 | 本設計での実装 |
| --- | --- | --- |
| 認知的負荷を増やさない | Sweller の認知負荷理論(extraneous load 削減)、Mayer のマルチメディア学習原則、NN/g の F 字型読解 | 1文書1型の厳守(3章)、1文60字目安(4章)、1段落1アイデア、結論先出し、progressive disclosure(8章)、注記の上限(6章) |
| ナラティブな成功体験 | Diátaxis tutorials 論、Carroll の Minimalism、85%ルール(Wilson et al.) | チュートリアル設計規定(9.4節): 開始5分以内の最初の成功、エラー回復の組み込み、結果の明示、励ましトーンの許可 |
| 実践できることが中心 | Google スタイル(task-oriented)、IBM 9特性(task orientation 筆頭)、Plain Language | how-to 中心の文書体系、1ステップ1アクション(6章)、コピー可能なコードブロック、hidden verb 回避 |

**原則の優先順位**: 規則同士が衝突したときは、「読者の成功」>「認知的負荷の削減」>「表記の統一」の順で優先する。例: 表記統一のために文が長くなるなら、文を短くする方を選ぶ。

**例外の思想**: 本ガイドはガイドラインであってルールではない(Google スタイルの思想を採用)。逸脱してよいが、逸脱する場合は PR に理由を一行書く。理由が繰り返し現れたら、それはガイド側を改訂するシグナルである(11章)。

## 3. レイヤー0: コンテンツ構造 (Diátaxis)

### 3.1 4つの型の定義

| 型 | 読者の状態 | 文書の役割 | 一言でいうと |
| --- | --- | --- | --- |
| tutorial (チュートリアル) | 初めて学ぶ。何ができるかまだ知らない | 手を動かして成功体験を得させる | 「やってみましょう」 |
| how-to (ハウツー) | 目的がある。やり方を知りたい | 特定の課題を解決する手順を示す | 「〜するには」 |
| reference (リファレンス) | 作業中。正確な情報を引きたい | 事実を網羅的・中立に記述する | 「〜の一覧・仕様」 |
| explanation (解説) | 立ち止まって理解を深めたい | 背景・理由・設計思想を説明する | 「なぜ〜なのか」 |

### 3.2 型の判定フロー

新しい文書を書くとき、次の2つの質問で型を決める。

1. **読者は「学んでいる」か「作業している」か?**
   - 学んでいる(まだ目的を持たない) → 左列
   - 作業している(具体的な目的がある) → 右列
2. **読者に必要なのは「行動(手を動かす)」か「知識(頭で理解する)」か?**
   - 行動 → 上段
   - 知識 → 下段

|  | 学習中 | 作業中 |
| --- | --- | --- |
| **行動** | tutorial | how-to |
| **知識** | explanation | reference |

判定に迷う典型例:

- 「Claude Code をはじめて使う人向けの導入手順」→ tutorial (学習+行動)
- 「Claude Code で PR レビューを自動化する手順」→ how-to (作業+行動)
- 「CLAUDE.md の設定項目一覧」→ reference (作業+知識)
- 「なぜ CLAUDE.md を階層化するのか」→ explanation (学習+知識)

### 3.3 混在禁止ルール

**1文書1型を厳守する。** 型の混在は extraneous load の最大要因である。

| アンチパターン | 症状 | 直し方 |
| --- | --- | --- |
| tutorial に reference が混入 | 手順の途中でオプション一覧・仕様表が現れる | 一覧は reference に切り出し、tutorial からリンクする |
| how-to に explanation が混入 | 手順の途中で設計背景の長文が現れる | 「理由は[解説記事]を参照」の一行リンクに置き換える |
| reference の tutorial 化 | 仕様書なのに「まず〜してみましょう」と語りかける | reference は中立・網羅・無感情に徹する |
| explanation の how-to 化 | 解説記事に番号付き手順が現れる | 手順は how-to に切り出す |

### 3.4 4型に当てはまらない文書の扱い

進捗管理・ロードマップ・スケジュールなど、読者に知識や手順を渡すのではなく、プロジェクトの状態を追跡するための文書は、Diátaxis の対象外である。これらは `docs/` 配下の4型構造に含めず、リポジトリ直下に置く(例: `ROADMAP.md`)。`docs/README.md` の4つの入口表を汚さないためである(SG-ADR-003)。

**リンク誘導の定型文** (混在の代わりに使う):

- 「ここでは HTTPS を使います。理由を知りたい方は[解説: なぜ HTTPS か]を参照してください。」
- 「その他のオプションは[リファレンス: ○○コマンド一覧]にあります。」

### 3.4 ディレクトリ構造

```text
docs/
├── README.md            # 入口。読者タイプ別の導線(8.5節)
├── tutorials/           # チュートリアル
├── how-to/              # ハウツー
├── reference/           # リファレンス
├── explanation/         # 解説
├── glossary.md          # 全文書共通の用語集(5.3節)
├── _templates/          # 付録Aのテンプレート4種
└── _style/              # 本ガイド・textlint設定・prh辞書
    ├── style-guide.md
    ├── .textlintrc.json
    └── prh-ai-terms.yml
```

- ファイル名は英小文字ケバブケース(`setup-claude-code.md`)。日本語ファイル名は使わない(リンク切れ・環境差異の原因)。
- 1ファイル1トピック。H5 が必要になったら文書を分割するシグナルとみなす(GitLab 方式)。

## 4. レイヤー1: 文体

### 4.1 基本トーン

Microsoft の3原則を日本語運用に翻訳して採用する。

| 原則 | 意味 | 実装 |
| --- | --- | --- |
| warm and relaxed | 温かくくつろいだ | ですます調。過剰な敬語(いたします・させていただきます)は使わない |
| crisp and clear | 歯切れよく明快 | スキャン優先。結論先出し。短文 |
| ready to lend a hand | 進んで手を貸す | 読者の失敗を先回りして拾う(エラー回復、9.5節) |

### 4.2 文体10原則 (OK / NG 例付き)

1. **ですます調で統一する。** 常体(である調)と混在させない。
   - OK: 「設定ファイルを作成します。」
   - NG: 「設定ファイルを作成する。次に起動します。」
2. **結論を先に書く (BLUF)。** 段落の最初の文で要点を言い切る。
   - OK: 「この設定は不要です。v2.0 から自動化されたためです。」
   - NG: 「v2.0 からの変更により自動化が進んだ結果として、この設定は不要になりました。」
3. **一文を短くする。** 目安60字、上限90字。読点が3つを超えたら分割する。
4. **一段落一アイデア。** 段落は2〜4文。話題が変わったら段落を変える。
5. **冗長表現を避ける。**
   - OK: 「変更できます」 / NG: 「変更することができます」
   - OK: 「確認します」 / NG: 「確認を行います」
6. **格助詞(が・の・を・に)を省略しない。**
   - OK: 「ファイルを保存します」 / NG: 「ファイル保存します」
7. **二重否定を使わない。**
   - OK: 「必ず設定してください」 / NG: 「設定しないわけにはいきません」
8. **能動態を優先する。** 動作の主体(あなた・システム)を明示する。
   - OK: 「コマンドを実行すると、ログが出力されます」
   - NG: 「コマンドが実行されるとログの出力が行われます」
9. **弱い表現を避ける。** 「〜と思います」「〜かもしれません」は手順書では禁止。explanation でのみ、根拠を添えた見解表明として許可する。
10. **肯定形で書く。** 何をするなではなく、何をするかを書く。
    - OK: 「変更前にバックアップを取得してください」
    - NG: 「バックアップを取得せずに変更しないでください」

### 4.3 型別トーン調整

文体10原則を土台に、型ごとに次の調整を加える。

| 型 | 人称・語りかけ | 特有ルール |
| --- | --- | --- |
| tutorial | 「〜しましょう」「一緒に〜します」。励まし(「できました!」)を許可 | 各ステップの末尾に期待される結果を書く。感嘆符は励まし用途に限り許可 |
| how-to | 命令形に近い簡潔体(「〜します」「〜してください」) | 前置きは3文以内。すぐ手順に入る |
| reference | 中立・記述体。語りかけない | 主観形容詞(便利な・簡単な)を使わない |
| explanation | 論述体。「なぜなら」「一方で」を使ってよい | 見解と事実を区別する(「筆者の見解では〜」) |

### 4.4 やさしい日本語の適用

audience に「事務」または「管理」を含む文書(8.2節)では、追加で次を適用する。

- **ハサミの法則**: はっきり言う・さいごまで言う・みじかく言う。
- カタカナ専門用語の初出には言い換えを併記する。例: 「リポジトリ(ファイルの保管場所)」。2回目以降は用語のみでよい。
- 情報を削る勇気を持つ。「表現を優しくする」前に「載せる情報を絞る」。優先度の低い情報は削除するか、リンク先に送る。

## 5. レイヤー2: 用語

### 5.1 表記の基本規則 (JTF 準拠)

| 規則 | OK | NG |
| --- | --- | --- |
| 全角文字と半角英数字の間にスペースを入れない | 「Claude Codeを起動」 | 「Claude Code を起動」※ |
| 長いカタカナ複合語は中黒で区切る | 「コンテキスト・エンジニアリング」 | 「コンテキストエンジニアリング」(4語以上の場合) |
| 英単語は原則半角 | 「GitHub」 | 「ＧｉｔＨｕｂ」 |
| 数字は半角算用数字 | 「3つの原則」 | 「三つの原則」「３つの原則」 |

※全角半角間スペースは「入れない」を標準とする。既存文書が「入れる」で統一されている場合はファイル単位で統一を維持し、prh では検出のみ行う。

### 5.3 用語集 (glossary.md) の運用

- 全文書横断で1つだけ持つ(Single Source of Truth)。文書ごとの用語集は作らない。
- 掲載基準: 非技術者が初見で分からない用語+社内固有の用語。
- 各エントリは「用語 / 一行定義 / 詳しい解説へのリンク(あれば)」の3要素。定義は50字以内。
- 文書側では初出の用語を用語集へリンクする。例: `[トークン](../glossary.md#トークン)`。
- 用語集の見出しアンカーが日本語になるため、リンク切れ検査を CI に含める(7.4節)。

## 6. レイヤー3: ビジュアル / フォーマット

### 6.1 見出し

- H1 は文書タイトルのみ。本文は H2 から始め、レベルを飛ばさない。
- 見出しだけを拾い読みして文書の流れが分かること(F 字型読解対応)。書き終えたら見出しだけを抜き出して通読し、ストーリーが通るか確認する。
- 見出しの先頭に意味のある語を置く。「について」「その他」で始めない。
  - OK: 「トークン上限の確認方法」 / NG: 「〜について」
- how-to の見出しは「〜する」体言止めまたは動詞終止。tutorial は「〜してみよう」を許可。

### 6.2 手順の書式

- 番号付きリストで書く。**1ステップ1アクション。**
- 各ステップは「操作 → 期待される結果」の順で書く。結果の明示は tutorial では必須、how-to では結果が自明でない場合に必須。

````markdown
1. ターミナルで次のコマンドを実行します。

   ```bash
   claude --version
   ```

   バージョン番号(例: `2.x.x`)が表示されます。

2. 表示されない場合は、[トラブルシューティング](#よくあるエラーと対処)へ進んでください。
````

- 手順が10ステップを超えたら、意味のまとまりで小見出しに分割する(チャンキング)。

### 6.3 注記 (NOTE / WARNING)

- 種類は2つだけに絞る: `> **NOTE:**`(補足) と `> **WARNING:**`(データ損失・課金・セキュリティに関わる警告)。
- **1ページあたり合計2個まで**を目安とする(GitLab の「note は控えめに」)。3個以上必要に感じたら、本文の構成を見直す。
- WARNING は該当ステップの直前に置く(直後ではない)。

### 6.4 コードブロック

- コマンド・コード・設定は必ずコードブロックで書く。**画像にしない**(コピー可能性の確保)。
- フェンスには必ず言語タグを付ける(`bash` / `json` / `yaml` / `text` など)。
- 実行コマンドと出力例を同じブロックに混ぜない。出力例は別ブロック(`text`)にする。
- プレースホルダーは `<山括弧>` で示し、直後に説明を置く。例: `ssh <ユーザー名>@<ホスト>`。

### 6.5 スクリーンショット規定 (AI ツール向け)

- **原則: 撮らない。** 文章とコードブロックで説明できるなら文章を優先する。「左上の検索アイコンをクリック」程度は文章で足りる。
- 撮ってよい条件: (a) 画面のどこを見るべきか文章で特定しにくい、(b) UI が比較的安定している、の両方を満たす場合のみ。
- ベータ機能・変更予告のある UI は撮らない。
- 撮る場合の規則:
  - 注目箇所を赤枠などで注釈する。
  - alt テキストを必ず書く(内容が伝わる一文)。
  - ファイル名は `対象-内容-YYYYMM.png`(例: `claude-code-settings-202607.png`)。撮影年月で陳腐化を判定できるようにする。
  - 元素材(注釈前)を `docs/_assets/raw/` に保管し、再撮影・再注釈を容易にする。

### 6.6 表

- 3項目以上の対比・対応関係は表にする。2項目なら本文で書く。
- 表のセル内では長文を書かない(1セル40字目安)。長くなるなら本文に戻す。
- モバイル閲覧を考慮し、列数は5列以内を目安とする。

### 6.7 完了判定 (Definition of Done)

読者が「自分は終わってよいのか」を自分で判定できるようにする。完了が曖昧な手順書は、読者(特に非技術者)に「これで合っているのか」という不安を残す。tutorial / how-to では、手順の直後(「よくあるエラーと対処」の前)に `## 完了の確認` を必須で置く。書式は次の4要素。

1. **確認操作**: 完了状態を確かめるコマンドまたは操作(あれば)。
2. **定型文**: 「次の状態になっていれば完了です。」
3. **完了条件**: チェックリスト形式(`- [ ]`)、1〜4項目。**「操作したこと」ではなく「観測できる状態」で書く**。
   - OK: 「`git log` の先頭に生成されたメッセージのコミットが表示される」
   - NG: 「コミットを実行した」(操作の記述であり、成否を判定できない)
4. **安心情報**(任意だが推奨): 「この手順の操作はここまでです」「やり直したい場合は〜で戻せます」など、完了後に何も壊れていないこと・引き返せることを一言添える。

10章のロードマップ表で各フェーズに完了条件を付けているのと同じ思想である。読者に対しても「何ができたら完了か」を先に約束し、その達成を読者自身に確認させることで、成功体験を確定させる。

### 6.8 レイアウト目的の HTML タグの禁止

本文にレイアウト・装飾目的の HTML タグを書かない。レイアウトは将来の HTML 化時にサイトテンプレート側で一括実装する(プレゼンテーション設計の分離)。手書きのレイアウトタグは、テンプレートと衝突して HTML 化の障害になる。

- 禁止例: `<div>` / `<span>` による装飾・配置、`<br>` による改行調整、`<font>` `<center>`、style 属性、表の代用としての `<table>` 手書き。
- 意味を持つ要素は例外として許可する: `<details>`(§8.4 の条件つき)、`<kbd>`(キー操作の表記)。
- 改行・余白を調整したくなったら、タグではなく構成で解決する(段落を分ける、リストにする、文書を分割する)。
- 判定基準: そのタグを削除しても**内容**が欠けないなら、それはレイアウト目的であり禁止対象である。

### 7.1 .textlintrc.json (フェーズ2導入時の実設定)

```json
{

    "preset-ja-technical-writing": {
      "sentence-length": {
        "max": 90
      },
      "max-ten": {
        "max": 3
      },

        "preferInHeader": "",
        "preferInBody": "ですます",
        "preferInList": "",

      "no-doubled-joshi": {

      },
      "no-exclamation-question-mark": false,

        "max": 6,

    }
  },
  "filters": {

  }

```

設定意図:

- `sentence-length: 90` — 文体原則3(上限90字)に対応。preset 既定の120字より厳しく、公式推奨の90字を採用。
- `no-exclamation-question-mark: false` — tutorial の励まし表現(「できました!」)を許可するため無効化。乱用は人間レビューで抑制する。
- `preferInList: ""` — 箇条書きは体言止め・ですます両方を許可する。当初「である」を指定していたが、フェーズ1の予行 lint で実文書の箇条書き(「対処: 〜してください。」等)と33件衝突したため変更した(SG-ADR-002)。
- `filters.comments: true` — どうしても除外したい箇所を `<!-- textlint-disable -->` で制御可能にする。ただし使用時は理由コメントを必須とする。
- `.textlintignore` — ルール文書(`_style/style-guide.md`・`writing-charter.md`)は NG 例を意図的に引用するため、テンプレート(`_templates/**`)はプレースホルダーを含む足場のため、lint 対象から除外する。
- prh の辞書では、短い語が長い語の内部にマッチする穴に注意する(例: 「プルリク」が「プルリクエスト」に部分一致)。負の先読み `/プルリク(?!エスト)/` で塞ぐ。ハイフンを含む素の文字列パターンは不正な正規表現に変換されるため、`/fine-?tuning/` のように正規表現形式で書く。
- フェーズ3で `preset-jtf-style` を追加する(5.1節の表記規則の機械化)。初期から入れないのは、指摘数が多すぎて導入初期の心理的負荷になるため。

- link-check は内部リンク(用語集アンカー含む)の切れを検出する。

### 7.5 レビューフロー (2段階)

1. **機械レビュー**: textlint + link-check (CI)。表記・文長・用語はここで完結させる。
2. **人間レビュー**: 内容のみに集中する。観点は次の5つだけ。
   - 型は正しいか(tutorial に reference が混ざっていないか)
   - 手順は再現できるか(可能ならレビュアーが1回実行する)
   - 対象読者(audience)に対して前提知識の明示は足りているか
   - 結論先出しになっているか(見出しだけ読んで流れが分かるか)
   - AI 特有規定(9章)を満たすか

**人間レビューで表記の指摘をしない。** 表記指摘が出た場合は prh 辞書か textlint 設定に追加して機械化する(レビューコストの構造的削減)。

## 8. 横断設計1: 混成読者対応

### 8.1 frontmatter 仕様 (全文書必須)

```yaml
---
title: Claude Code をはじめて使う
type: tutorial            # tutorial | how-to | reference | explanation
audience: [se, admin]     # se | admin | manager (複数可)
level: 初級               # 初級 | 中級 (tutorial / how-to のみ)
time: 30分                # 想定所要時間 (tutorial / how-to のみ)
owner: hide               # 単一個人。チーム名は不可
review-by: 2026-10-18     # 鮮度期限 (9.2節)
freshness-class: S        # S | A | B (9.2節)
---
```

- frontmatter は文書の1行目から `---` で始める。CI でスキーマ検査を行う(フェーズ3以降)。
- `owner` は必ず個人名。「全員の所有物は誰の所有物でもない」ため、チーム名・ロール名を認めない。

### 8.2 ロールバッジ仕様

文書冒頭(H1 直後)に対象読者バッジを表示する。Claude Code 運用マニュアル v1.6 のバッジ体系と統一すること(表記が異なる場合は v1.6 側を正とし、本節を改訂する)。

| バッジ | 意味 |
| --- | --- |
| `🟢 全員` | 事務・管理を含む全メンバーが対象 |
| `🔵 SE` | エンジニア向け。CLI・設定ファイルの操作を含む |
| `🟡 事務・管理` | 非エンジニア向け。ブラウザ/GUI 操作のみで完結する |

表示例:

```markdown
# Claude Code をはじめて使う

`🟢 全員` `⏱ 30分` `📶 初級`
```

- バッジは frontmatter の値から機械的に導出できる内容に限る(二重管理の禁止)。将来的に静的サイト生成へ移行する場合は自動生成に切り替える。

### 8.3 前提知識ブロック

tutorial / how-to の冒頭に必須。書式:

```markdown
## はじめる前に

**必要なもの**

- GitHub アカウント(組織 org への招待済み)
- Node.js 20 以降

**前提知識**

- ターミナルの基本操作([入門チュートリアル](../tutorials/terminal-basics.md)を完了していること)
```

- 前提知識には可能な限り社内文書へのリンクを付け、「読者が前提を満たしていない場合の次の一手」を示す(Mayer の Pre-training 原則の実装)。
- 前提が3項目を超える tutorial は、対象読者設定が広すぎる可能性がある。分割を検討する。

### 8.4 読者分岐 (progressive disclosure)

単一文書内で読者レベルを分岐させる場合の定型パターン:

- **打ち切り宣言**: 「ここまでで基本操作は完了です。日常業務にはこの範囲で十分です。」の一文を、非技術者向けゴール地点に必ず置く。
- **深掘り誘導**: その直後に「仕組みを知りたい方は[解説: ○○]へ」「カスタマイズしたい方は[ハウツー: ○○]へ」のリンクを置く。
- 折りたたみ (`<details>`) は GFM では動作するが移植性が低いため、リンク誘導を優先する。使う場合は「クリックで展開」であることを summary 行に明記する。

### 8.5 入口ページ (docs/README.md)

F 字型読解を前提に、上部に読者タイプ別導線を置く。

```markdown
# 社内 AI ナレッジベース

## あなたに合った入口

| はじめての方 | 業務で使いたい方 | 仕様を調べたい方 | 深く理解したい方 |
| --- | --- | --- | --- |
| [チュートリアル一覧](tutorials/) | [ハウツー一覧](how-to/) | [リファレンス一覧](reference/) | [解説一覧](explanation/) |

分からない用語があれば[用語集](glossary.md)へ。
```

## 9. 横断設計2: AI 研修コンテンツ特有規定

### 9.1 適用範囲

Claude Code・生成 AI・LLM 関連のすべての文書。変化の速さが従来の社内技術文書と桁違いであるため、以下を上乗せ規定とする。

### 9.2 鮮度管理

**freshness-class (変化速度クラス)** を frontmatter で必須指定する。

| クラス | 対象例 | review-by の上限 |
| --- | --- | --- |
| S | ツールの UI・コマンド・料金・モデル名に依存する文書 | 発行から1ヶ月 |
| A | ワークフロー・ベストプラクティス(ツール依存が薄い) | 発行から3ヶ月 |
| B | 概念解説・設計思想(explanation の多く) | 発行から12ヶ月 |

運用:

- `review-by` を過ぎた文書は、冒頭に警告バナー(「この文書は YYYY-MM-DD 以降レビューされていません」)を表示する。フェーズ4で bot による自動リマインド(週次で owner にメンション)を導入する。
- レビューの成果は「更新」または「期限延長(内容確認済み)」のどちらかを commit として残す。黙って放置された文書を作らない。
- 廃止時は削除せず、冒頭に「⚠ この文書は廃止されました。後継: [リンク]」を残して3ヶ月後に削除する(リンク切れと迷子の防止)。

### 9.3 非決定的出力の書き方

LLM の出力は毎回異なる。読者が「例と違う=失敗」と誤解しないため、入力(プロンプト)を示す箇所は次の**4点セット**で書くことを義務付ける。

1. **入力**のコードブロック。
2. **定型文**: 「出力は一例です。表現は実行のたびに変わりますが、次のような応答が返ります。」
3. **具体的な出力例**の `text` ブロック。実際の応答の形(構成・分量感)が伝わるよう省略せずに示す。
4. **成功判定基準**: 「次の要素が含まれていれば成功です。」+箇条書き(例: 「テストコードが生成されている」「対象関数名が含まれている」)。

出力例は「形」を伝え、判定基準は「成否」を伝える。どちらか一方では足りない。期待結果を一言一句で保証する書き方はしない。

### 9.4 チュートリアル設計チェックリスト (ナラティブな成功体験の実装)

tutorial 型の文書は、公開前に次をすべて満たすこと。

- [ ] **冒頭でゴールを見せる**: 「このチュートリアルを終えると、〜ができるようになります」+完成形のイメージ(出力例・成果物)。
- [ ] **開始5分以内に最初の成功体験がある**(コマンド1つで目に見える結果が出る等)。
- [ ] 各ステップに期待される結果が書かれている(約束と達成の反復)。
- [ ] **難易度が階段状**: 序盤は失敗しようがない手順、終盤にやや挑戦的な応用を1つ。全体として「8割は確実に成功する」設計(85%ルールの運用近似)。
- [ ] **繰り返しの仕掛け**: 学んだ操作をパラメータを変えてもう一度やらせるステップがある。
- [ ] 選択肢を出さない。方法が複数あっても、最短で成功する1つだけを書く(他は how-to へ)。
- [ ] 説明したい衝動を我慢した。背景・理論は explanation へのリンクにした。
- [ ] 最後に「できたこと」を振り返り、次のチュートリアル/ハウツーへ誘導している。

### 9.5 エラー回復セクション (tutorial / how-to 必須)

Minimalism の error recovery を制度化する。

- 文書末尾に `## よくあるエラーと対処` を必須で置く。最低1項目、上限5項目。
- 書式: 「症状(表示されるメッセージ・状態) → 原因 → 対処」の3点セット。症状は読者が画面で見る文言をそのまま書く(検索可能性)。
- エラーを恥ではなく通常ルートとして書く。トーン例: 「このエラーは初回設定でよく発生します。」
- 5項目で足りない場合は、独立したトラブルシューティング文書(how-to 配下)に切り出してリンクする。

## 付録B: 執筆前クイックチェック (1枚もの)

書き始める前に30秒で確認する。

1. この文書の型は? (tutorial / how-to / reference / explanation) — 迷ったら3.2の2つの質問。
2. 読者は誰? (se / admin / manager) — admin を含むならやさしい日本語(4.4)。
3. 前提知識は3項目以内に収まるか? — 超えるなら分割。
4. 5分以内の成功はあるか? (tutorial のみ)
5. 完了条件を「観測できる状態」で書けるか? (tutorial / how-to のみ) — 書けない=完了の定義が曖昧なサイン。
6. よくあるエラーを最低1つ書けるか? (tutorial / how-to のみ) — 書けない=自分で実行していないサイン。
