# 標準ワークフローでタスクを進める

`🔵 SE` `⏱ 15分` `📶 中級`

この手順では、Claude Code でタスクに取り組むときの標準ワークフロー「探索 → 計画 → 実装 → コミット → レビュー」を実践します。

## はじめる前に

- セットアップ済みの Claude Code([Claude Code の個人環境をセットアップする](setup-claude-code.md)を完了していること)
- 取り組む具体的なタスク(バグ修正や機能追加など)

## 手順

1. **探索: plan モードでコードを読ませる**

   `Shift+Tab` で plan モード(読み取り専用)に切り替え、関連コードを調べさせます。この段階では編集させません。

   ```text
   注文キャンセル機能にバグがある。まず関連するファイルを調べて、
   処理の流れを説明して。まだコードは書かないで。
   ```

   > **WARNING:** 探索と計画を飛ばすと、Claude が解決策のコーディングに直行してしまい、品質が下がります(公式明言)。ただし1行修正レベルの軽微な変更なら、計画は省略できます。

2. **計画: 実装計画を出させ、承認する**

   ```text
   原因が分かったら、修正の実装計画を箇条書きで出して。
   影響範囲と、変更しないファイルも明記して。
   ```

   出てきた計画は `Ctrl+G` でエディタを開いて直接修正できます。計画の承認は人間の仕事です。

3. **実装: 検証手段をセットで与える**

   Claude は、作業が完了したように見えると止まります。テスト・ビルド・リンターなど、正しさを機械的に確認できる手段を完了条件として指定します。仕様が明確なタスクでは、先に入出力ペアからテストを書かせ、失敗を確認してから実装させる TDD(テスト駆動開発)も有効です。

   ```text
   計画に沿って実装して。完了条件は
   「npm testが全件パスすること」。
   パスするまで自分で修正を繰り返して。
   ```

4. **コミット: こまめにチェックポイントを作る**

   こまめなコミットは、AI 作業の「セーブポイント」です。失敗したら `/rewind` や git で戻れます。区切りのよいところで、コミットと PR 作成まで進めます。

5. **レビュー: 別セッションで Writer / Reviewer を分離する**

   実装した Claude 自身にレビューさせると、自分の書いたコードに甘くなります。新鮮な目で見ることで、直前に書いたコードへの肩入れを避けられます。レビューは別セッション、またはレビュー用のサブエージェントで行います。

   ```text
   /code-review
   ```

   > **NOTE:** レビュー役には「正しさや明示された要件に影響するギャップだけを指摘して」と伝えると、過剰設計の提案を防げます。

## 完了の確認

```bash
git log --oneline -5
```

次の状態になっていれば完了です。

- [ ] 探索・計画のやり取りが会話に残っている(実装だけを依頼していない)
- [ ] `git log` に、区切りのよい単位のコミットが複数並んでいる
- [ ] 別セッションまたは `/code-review` でコードレビューを実施した

この手順の操作はここまでです。途中で計画を見直したい場合は、そのステップまで会話を戻すか、`/clear` からやり直してください。

## よくあるエラーと対処

### 探索を頼んだのに、いきなりコードを書き始める

- 原因: plan モードへ切り替えずに依頼しています。
- 対処: `Shift+Tab` で plan モードに切り替えてから、同じ依頼をやり直してください。

### 実装が「完了しました」と言うが、テストが通っていない

- 原因: 完了条件を指定していません。
- 対処: 「npm test が全件パスすること」のように、機械的に確認できる完了条件を明示して依頼し直してください。
